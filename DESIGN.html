Nine-Session Relay

How to grow the three-session relay you already have into a pipeline that classifies an incoming requirement, picks the model the work deserves, routes it to the specialist that handles that kind of work, reviews the output twice independently, and hands back either the exact text to paste or the steps to follow.

The whole structure

One session takes the requirement and decides what kind of work it is. A second decides what model the work deserves. One specialist does the work on that model. Two reviewers judge it without seeing each other. A result session turns a pass into either pasteable text or a guide you follow — and a fail into a reason plus a redo.

Three things in this picture carry most of the design. The four workers are alternatives, not stages — classification happens once and no later hop re-decides it. The fail arrow goes two places at once, because the result session needs the reason to show you and the orchestrator needs it to make the redo specific. And the dashed rail on the right is the point: no session remembers the state of a task, it reads it.

What changes from what you have

The current relay/ is a working three-session pipeline: orchestrator → worker → reviewer → orchestrator. It already has the parts that are hardest to get right — an atomic task ledger, a state machine that rejects illegal transitions, an attempt cap the model cannot argue its way past, and an envelope format that carries reply-to through every hop. None of that needs rewriting.

Keep

The instinct behind the existing design is the right one and should survive the expansion: anything that must not drift lives in relay.mjs, not in a prompt. Attempt counting, the retry cap, which hop comes next, which model is pinned, whether two reviews are in — all of it is arithmetic the CLI does and prints. A session's job is to read the printed NEXT: line and obey it.

The nine roles

Each role is a separate Claude Code session with its own working directory and its own CLAUDE.md pointing at its contract in relay/roles/.

Roleroutes keyOwns
OrchestratororchestratorTalks to you. Reads the requirement, assigns a kind and an output_mode, dispatches, and re-dispatches on a fail. Never does the work.
Model analystmodel-analystReads the same requirement and pins the model for the worker and for the reviewers. Judges difficulty, not content.
Answer workerworker-answerPicks the selections and drafts the explanation. Bound by the DA answer-style rules already in memory.
Repo workerworker-repoFinds the hardest real repo matching the brief. Scores candidates against a fixed rubric.
Project workerworker-projectScaffolds a new project to spec.
Prompt workerworker-promptWrites prompts designed to make models fail, with the expected failure named in advance.
Reviewer Areviewer-aCompliance. Walks the requirement clause by clause and checks each one landed.
Reviewer Breviewer-bCorrectness. Ignores the checklist and attacks the substance — verify the facts, open the links, run the thing.
ResultresultThe only writer of the payload. Produces the paste text or the guide, or the reason on an escalation.

Splitting the reviewers on axis rather than duplicating them is what makes the second review worth its cost. Two sessions running the same checklist agree with each other for the same reasons; a compliance pass and a correctness pass fail on different things. Reviewer A catches "you never answered part 3." Reviewer B catches "part 3 is answered and the answer is wrong."

Splitting the model analyst out from the orchestrator is the same instinct applied one step earlier. The orchestrator is deciding what the work is, and a session that has just settled that question is poorly placed to also judge how hard it will be — the classification feels finished, so the work feels understood. A session whose only job is difficulty reads the requirement cold and asks one question about it.

Fewer terminals

Roles are addresses, not processes. Pointing the four worker keys at one session collapses the row to five terminals, and the contract that session loads is still chosen by kind. The two reviewers are the one pair you should not collapse — independence is the whole point, and a single session holding both opinions has already read its own first verdict. The model analyst can share a session with the orchestrator if you must, at the cost described above.

Model selection

The model is a property of the task, not of the session that happens to pick it up. Choose it once, record it, and make every downstream hop honour it.

The analyst sits between classify and assign. It reads the requirement and any attachment, then records two picks — the model the worker runs on, and the model the reviewers run on — with a written reason for each:

node relay/bin/relay.mjs model t-m1x8k2 --work opus --review opus \
     --why "single-file repo trap; the whole task is catching an inconsistency
            two modules apart, and a miss is invisible in the output"

assign then refuses to dispatch a task whose model is unset, exactly as it already refuses one whose kind is unset. That single guard is what turns the analyst from advice into a step.

Choosing

PickWhenTypical here
opusBeing wrong is expensive and the error would be quiet. Long multi-file reasoning, adversarial design, anything where the output looks the same whether it is right or not.repo hunt · prompt authoring · both reviewers on a graded task
sonnetThe shape of the work is already settled and the job is to execute it well.project scaffolding · bounded edits · well-specified answer tasks
haikuMechanical, high-volume, low-ambiguity.reformatting · extraction · first-pass triage
fableSelectable alongside the others. Pin it for task kinds you have actually measured it on rather than by default.—

Rules the analyst follows

  • Reviewers are never weaker than the worker. A reviewer that cannot follow the reasoning it is checking rubber-stamps it, and you have paid for two reviews and received one.
  • A redo bumps the worker model up if a stronger one exists, or records why it did not. Re-running attempt 2 on attempt 1's model is the most common way to get an identical second failure.
  • Judge difficulty, not topic. A short question can be the hard one. What matters is how far apart the pieces of the answer are and how visible a mistake would be.
  • Write the reason. A reviewer who thinks a task was under-modelled needs something concrete to point at, and --why is the only record of what the analyst was thinking.

How the pin is actually applied

Constraint

A Claude Code session cannot change its own model mid-session. Writing model: opus into an envelope and trusting the receiving session to honour it does nothing on its own. The pin needs a mechanism.

Mechanism A — subagent override. The worker session reads model: from the envelope header and runs the actual work in a subagent with that model set, then records built and sends onward itself. The parent session stays on whatever model it was started with; only the reasoning that matters runs on the pinned one. The same applies to each reviewer. The one constraint is that the subagent does the work and returns — it must not make the cross-session sends, because those go out under the parent's address and the reply lands with the parent.

Mechanism B — model-pinned sessions. Bootstrap one session per role-and-model pair you actually use, set each one's model with /model at bootstrap, and let routes.json carry it: worker-repo@opus, worker-repo@sonnet. No delegation at all, at the cost of more terminals.

Start with A. It costs one extra hop inside the worker session and keeps the session count at nine. B is worth it only once you are running the same shape of task often enough that the terminals pay for themselves.

Ledger and state machine

One JSON file per task in relay/tasks/, written temp-then-rename so a peer session never reads a torn file. The transition table is the contract:

// relay.mjs — anything not listed is rejected
const LEGAL = {
  open:       ['classified'],
  classified: ['assigned'],
  assigned:   ['built'],
  built:      ['reviewing'],
  reviewing:  ['passed', 'failed'],
  failed:     ['assigned', 'escalated'],
  passed:     ['delivered'],
  escalated:  ['delivered'],
  delivered:  [],
};
open→ classified→ assigned→ built→ reviewing→ passed→ delivered
on fail: reviewing→ failed→ assigned (under cap) · failed→ escalated→ delivered (at cap)

Two of these states are new, and both exist to give a hop somewhere unambiguous to stand.

classified separates "a requirement arrived" from "we know what kind of work this is." Without it, kind gets decided implicitly at assign time and there is no record of why. It is also where the model analyst does its work: the task sits in classified from the moment the orchestrator hands it over until assign finds both kind and model populated.

delivered separates "the reviewers approved" from "the thing you paste or follow exists." A task sitting in passed has been judged but not yet written up, and relay list shows you the difference at a glance.

Alternative

You could give the model pick its own state — classified → modelled → assigned — instead of guarding assign. It makes relay list show exactly which session is holding a stalled task, at the cost of one more transition to maintain. Worth doing if the analyst turns out to be where tasks get stuck; not worth it up front.

The two-review gate

The requirement is that nothing reaches you without being checked at least twice. Enforce it structurally: the verdict is not a call any single reviewer makes.

// both slots must be recorded; the second one to land resolves the task
review(a) {
  withLock(id, () => {
    const t = load(id);
    if (t.reviews[slot]) die(`slot ${slot} already recorded this attempt`);
    t.reviews[slot] = { result: a.result, notes: a.notes, by: a.by, at: now() };

    const other = slot === 'a' ? 'b' : 'a';
    if (!t.reviews[other]) {
      save(t);
      return log(`NEXT: WAIT. The other reviewer resolves this task.`);
    }
    const passed = t.reviews.a.result === 'pass' && t.reviews.b.result === 'pass';
    save(move(t, passed ? 'passed' : 'failed', a.by));
    // ...print the routing instruction for whichever verdict landed
  });
}

Three details make this hold up.

Independence

relay show <id> --for a replaces the b slot with "(hidden)" and vice versa. A reviewer reading the task file cannot see the other's verdict, so the second review is a second opinion rather than a ratification of the first. Reviewers need the spec, the attachments and build_notes; they do not need each other.

Freshness

relay assign clears reviews before incrementing the attempt. A redo is judged from scratch. Without this, a reviewer who passed attempt 1 has a stale pass sitting in the slot, and attempt 2 resolves on one real review.

Concurrency

Both reviewers can finish at the same moment and both will read-modify-write the same file. mkdir is atomic on NTFS and POSIX, so a lock directory next to the task file is enough; stale locks older than thirty seconds are reclaimed. This is the one place in the relay where genuine parallelism exists, and it is worth the twelve lines.

Failure mode

If you skip the lock, the interleaving that loses a review is not rare and not loud. Both reviewers load a record with an empty reviews, each writes its own slot, the later write wins, and the task sits in reviewing with one review recorded and both reviewers convinced they are done. Nothing errors. The task just stops.

Two kinds of result

What you need at the end is not always the same shape. Sometimes it is text that goes straight into a field. Sometimes it is a set of steps you have to carry out yourself, because the requirement asks for something done on a machine the relay does not touch. The record carries which, as output_mode, set by the orchestrator at classify time.

ModeWhat the payload isWhat makes it wrong
pasteThe exact characters that go in the ticket or the form field, and nothing else. Selections first, then each explanation block under the question it belongs to.Any commentary that would be pasted along with it — a preamble, a sign-off, a note about what was checked. If you have to edit it before pasting, it failed.
guideNumbered steps you perform, each with the exact command or the exact click, and a checkpoint that tells you it worked before you move on.A step that describes an intention rather than an action, or one with no way to tell whether it succeeded.

Setting the mode at classify time rather than at delivery is deliberate. It changes what the worker produces, not just how the result session writes it up — a worker that knows the output is a guide records the commands it ran and the output it saw, and a worker that knows the output is paste text writes to the form's structure. It also gives Reviewer A something concrete to check: a paste payload with explanatory prose in it is a compliance failure, and a guide with an unverifiable step is too.

node relay/bin/relay.mjs deliver t-m1x8k2 --mode paste --file payload.md
node relay/bin/relay.mjs payload t-m1x8k2      # prints it, ready to copy

deliver refuses if --mode disagrees with the output_mode on the record. That catches the case where the result session read the work and decided for itself what shape the answer should be, which is the one judgement call it is not entitled to make.

For the answer worker and the result session, the DA rules already in memory are part of the contract — the voice, the two-paragraph ceiling, the twice-verified links, the numbered Q1 / Q2 output format. Reference them from roles/WORKER-ANSWER.md and roles/RESULT.md rather than restating them, so there is one copy to correct when a project's rules change.

CLI surface

Every command prints a NEXT: line. That line is the routing instruction, and sessions follow it rather than reasoning about what should happen next.

CommandRun byEffect
new --title T --spec-file F [--attach IMG] [--cap N]orchestratorCreates the record, copies attachments into tasks/<id>.files/, prints the id.
classify <id> --kind K --mode paste|guide --why "…"orchestratorSets kind and output mode. Refuses without a reason.
model <id> --work M --review M --why "…"model analystPins both models on the record.
assign <id>orchestratorattempt++, clears reviews. Refuses without a kind or a model, and at cap.
built <id> --notes "…"workerRecords the claim. Refuses empty notes.
review <id> --slot a|b --result pass|fail --notes "…"reviewerRecords one slot; resolves if it is the second.
escalate <id>orchestratorCap reached, no more redos.
deliver <id> --mode paste|guide --file FresultStores the payload. Refuses on a mode mismatch, or on a task that still owes a redo.
payload <id>anyonePrints the final text.
envelope <id> --to model-analyst|worker|reviewer-a|reviewer-b|orchestrator|resultevery hopBuilds the wire message. --to worker resolves through kind.

Note which flags are mandatory. --why on classify and on model, --notes on built and review: each is a place where an empty string would have let a session skip the part that makes the next hop possible. The CLI refusing is cheaper than a reviewer discovering at read time that build_notes says "done".

The task record

{
  "id": "t-m1x8k2", "title": "Rate the two responses on factuality",
  "spec": "…full requirement text…",
  "attachments": ["…/tasks/t-m1x8k2.files/form.png"],

  "kind": "answer",
  "kind_why": "asks for selections plus an explanation, no repo or build involved",
  "output_mode": "paste",

  "model": { "work": "opus", "review": "opus" },
  "model_why": "every claim needs a source checked twice; a missed one is invisible",

  "state": "reviewing", "attempt": 2, "cap": 3,
  "build_notes": "…what the worker produced, with paths and file:line refs…",
  "last_defects": "…the previous attempt's combined review notes…",
  "reviews": {
    "a": { "result": "pass", "notes": "…", "by": "rev-a-7", "at": "…" }
  },
  "review_notes": "", "payload": "",
  "history": [ { "at": "…", "from": "built", "to": "reviewing",
                 "actor": "rev-a-7", "attempt": 2, "note": "picked up" } ]
}

last_defects is the field that makes a redo worth running. It is populated from review_notes at assign time, before the reviews are cleared, and the worker envelope appends it under a heading that says to fix those specific things and leave the rest alone. A redo without it regresses the parts that already passed.

Envelope format

Sessions address each other by name via SendMessage. The envelope is what gets sent, generated rather than typed so that reply-to, the model pin and the attachment list survive every hop.

[TASK t-m1x8k2 | kind=answer | mode=paste | attempt 2/3 | state=assigned]
reply-to: qa-2-99
next-hop: answer-session-4
model: opus          # run the work in a subagent on this model
task-file: C:\…\relay\tasks\t-m1x8k2.json
attachment: C:\…\relay\tasks\t-m1x8k2.files\form.png
---
Rate the two responses on factuality

…spec…

## DEFECTS FROM ATTEMPT 1 — fix these, do not re-architect the rest
[review a - pass] every form field is answered…
[review b - fail] the cited URL 404s; the claim about the 2019 ruling is
unsupported by the source given…

reply-to always names the orchestrator. It is not the sender. This matters most at the reviewer, where the incoming message's from is the worker — a reviewer that replies to from sends its verdict back to the worker and the loop dead-ends one hop short of you. Generating the envelope from routes.json instead of typing an address removes the chance to get it wrong.

Requirements that arrive as images

Screenshots of a task form are a normal input, and the handling rule is short: the image travels by path, and every session opens it itself.

relay new --attach shot.png copies the file into tasks/<id>.files/ so it lives as long as the task does, and every envelope carries an attachment: line. The orchestrator reads the image to classify it. The model analyst reads it to judge difficulty. Each worker and both reviewers read the same file again.

Do not

Do not let the orchestrator transcribe the image into spec and drop the file. The transcription is the orchestrator's reading of the requirement, and if it missed a checkbox or misread a scale label, both reviewers will now check the work against the same mistake and both will pass it. The reviewers' value depends on their seeing the original.

Put the transcription in spec if it helps — just keep it labelled as a reading of the attachment rather than as the requirement, and keep the attachment.

The repo-hunting rubric

This is the worker where "do your best" fails, because there is no signal in the output that tells a reviewer whether the chosen repo was the hardest available or merely the first plausible one. The fix is to make the search itself the deliverable: the worker reports a scored table, and the reviewer re-derives the score.

The contract in roles/WORKER-REPO.md should require at least five candidates scored before a pick, and should score each on:

DimensionWhat actually makes a model fail
Coexisting subsystemsTwo implementations of the same concern living side by side, both writing the same state. The single strongest predictor — it forces the model to hold two mental models at once.
Documentation that liesDocstrings and comments describing intent the code does not implement. A model that trusts prose over control flow answers confidently and wrongly.
Cross-cutting stateAsync, caching, permission layers, signal handlers — behaviour that is not local to the file you are reading.
SpreadNon-test LOC and module count, so the answer is not in one file. Record the number, not an impression.
ProvenanceA real production codebase with real history, not a synthetic or toy repo. Stars and issue activity as a proxy.
ConstraintsWhatever the brief actually caps — size on disk, language, license, structure.

Two hard requirements on top of the score. The repo must be verified to resolve — clone it or hit the API, never cite one from memory. And the pick must be pinned to a commit, because an unpinned pick means line numbers in the ground truth drift out from under everyone downstream.

Worked example

The Saleor pick in GUIDE.md is what a good entry looks like: a legacy Payment model and a newer TransactionItem model coexisting and writing the same order fields, docstrings that describe a branch order the code does not implement, 261,848 non-test LOC, 61 MB, pinned at abfc51a. Every one of those is a checkable number rather than a judgement, which is exactly why a reviewer can confirm or reject it.

Invariants the CLI cannot enforce

These live in roles/ because they are about what a session chooses to do, not about what the ledger permits. Each one is a way the loop breaks quietly.

  • The worker never replies to the orchestrator. Its next hop is both reviewers, even when it is confident and even when the attempt number is high. The one exception is a genuine blocker — a contradictory spec, or an action its permissions refuse — which goes back to reply-to and stops there.
  • The reviewer sends to reply-to, not to from. from is the worker.
  • Only the reviewer that resolves the task routes anything. The first one to record reads NEXT: WAIT and stops. Two sessions both routing a verdict produces two redos of the same attempt.
  • The model pin is honoured, not noted. A session that reads model: opus and then does the work itself on whatever it was started with has silently discarded the analyst's step, and nothing downstream can tell.
  • Subagents do work and return; they do not send. A subagent's cross-session sends go out under its parent's address, and replies land with the parent — the subagent never hears back. The parent records the state transition and does the send.
  • No session performs work another session's permissions blocked. That launders your permission decision through a peer. Blocked work goes back to you.
  • Attachments travel as paths. Covered above, and it is the one most likely to be violated by a session trying to be helpful.
  • The result session writes the payload; nobody else narrates the answer to you. If the orchestrator also summarises the result, you now have two versions of the deliverable and no way to tell which one was reviewed.

Build order

Numbered because it is genuinely sequential — each step leaves the relay in a runnable state, so you can stop after any of them.

STEP 1Extend relay.mjs

Add the KINDS map (kind → routes key), the two new states, the withLock helper, and the classify / model / review / deliver / payload commands. Change assign to guard on kind and model, clear reviews, and populate last_defects. Change envelope to resolve --to worker through kind and to emit model: and attachment: lines. Change show to accept --for. Retire the old single-shot verdict command. The existing three-session flow keeps working throughout.

STEP 2Expand routes.json

Nine keys. Leave them as PLACEHOLDER-* until sessions exist; envelope refuses to build a message for an unpinned hop, which is the error you want rather than a send into the void.

STEP 3Write the role contracts

Rewrite ORCHESTRATOR.md for the classify step, the hand-off to the analyst, and the split fail-routing. Write MODEL-ANALYST.md new, with the rubric and the four rules from above. Rewrite REVIEWER.md for slots and independence, then fork it into REVIEWER-A.md (compliance) and REVIEWER-B.md (correctness) — the shared half stays in REVIEWER.md and each fork loads it. Keep WORKER.md as the common preamble, including the subagent-override instruction, and add the four specialist contracts. Write RESULT.md new, covering both output modes.

STEP 4Create the session directories

One directory per role under relay/sessions/, each with a CLAUDE.md of about six lines: which contract to read before responding to any cross-session message, and the path to the CLI. Short on purpose — the contract is the thing that changes, and it should change in one place.

STEP 5Bootstrap

Open a Claude Code session in each directory. Ask each to run ListAgents and report its own session name — the listing names the current session on its first line. Pin all nine with relay routes. Re-pin after any restart; session names do not survive one.

STEP 6Dry run

Put a task through that you already know the answer to, and check four specific things: that a deliberately bad build gets caught by both reviewers for different reasons, that assign refuses without a model and at the cap, that the redo envelope actually carries the defects, and that the worker really did run on the pinned model. Those four are where this design earns its keep, and they are the four that fail silently if a contract is worded loosely.

Running a task

# orchestrator
node relay/bin/relay.mjs new --title "Factuality SxS pair 14" \
     --spec-file spec.md --attach form.png --cap 3
node relay/bin/relay.mjs classify t-m1x8k2 --kind answer --mode paste \
     --why "selections plus an explanation; goes straight into the form"
node relay/bin/relay.mjs envelope t-m1x8k2 --to model-analyst

# model analyst
node relay/bin/relay.mjs model t-m1x8k2 --work opus --review opus \
     --why "every claim needs a source checked twice; a miss is invisible"
node relay/bin/relay.mjs envelope t-m1x8k2 --to orchestrator

# orchestrator
node relay/bin/relay.mjs assign t-m1x8k2
node relay/bin/relay.mjs envelope t-m1x8k2 --to worker     # SendMessage verbatim

# answer worker — reads model: opus from the header, works in a subagent on it
node relay/bin/relay.mjs show t-m1x8k2
node relay/bin/relay.mjs built t-m1x8k2 --notes "…"
node relay/bin/relay.mjs envelope t-m1x8k2 --to reviewer-a
node relay/bin/relay.mjs envelope t-m1x8k2 --to reviewer-b

# reviewer b, finishing first
node relay/bin/relay.mjs show t-m1x8k2 --for b
node relay/bin/relay.mjs review t-m1x8k2 --slot b --result fail \
     --notes "cited URL 404s; the 2019 ruling claim is unsupported by that source"
# → NEXT: WAIT. stops here.

# reviewer a, finishing second — resolves
node relay/bin/relay.mjs review t-m1x8k2 --slot a --result pass --notes "…"
# → VERDICT: FAILED (1/3) · NEXT: REDO
node relay/bin/relay.mjs envelope t-m1x8k2 --to result
node relay/bin/relay.mjs envelope t-m1x8k2 --to orchestrator

Add notify_when_idle: true to each SendMessage rather than polling ListAgents or sending "are you done?" — delivery is not acknowledged, and idle notification is how you find out a hop stalled.

Limits worth knowing before you rely on it

  • Sessions are ephemeral; the ledger is not. routes.json needs re-pinning after any restart, but tasks/ survives, so an in-flight task resumes by re-pinning and re-sending the envelope for its current state.
  • Delivery is not acknowledged. If a peer session has ended, the send does not land and nothing reports it. A task stuck in assigned for a long time usually means the worker session is gone, not that the work is hard.
  • The model pin is a convention, not a sandbox. Nothing verifies after the fact that a worker actually ran its subagent on the pinned model. If that matters, have the worker record the model it used in build_notes and make Reviewer A check it.
  • One worker per task. The lock covers the two reviewers, which is the only intended parallelism. Fanning one task out to several workers at once is outside what the ledger models.
  • Two reviews cost roughly what the work cost. That is the trade being made deliberately. If throughput matters more than it does today, lower --cap before weakening the gate — a task that fails twice is usually mis-specified rather than badly built, and a third attempt rarely fixes it.
  • The gate checks the work, not the requirement. If the requirement itself was misread at intake, both reviewers can pass a task that answers the wrong question. Classification's --why and the preserved attachment are the defences; neither is airtight.
